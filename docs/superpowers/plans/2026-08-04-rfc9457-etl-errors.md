# RFC 9457 ETL Error Contract Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace plain-text ETL failures with stable, non-sensitive RFC 9457 problem responses while preserving the successful endpoint contract.

**Architecture:** `EtlService` emits typed request exceptions carrying an enum-only error classification. `EtlController` preserves typed request and data-access failures while wrapping only unexpected runtime failures raised during the service invocation. A controller-scoped `@RestControllerAdvice` maps those explicit boundaries to fixed `ProblemDetail` responses with stable machine codes and request-URI instances without capturing unrelated Spring MVC routing or negotiation failures.

**Tech Stack:** Java 25, Spring Boot 3.5, Spring MVC `ProblemDetail`, Spring JDBC exceptions, JUnit 5, MockMvc, Mockito.

## Global Constraints

- Keep `POST /api/etl/process` success responses at `200` with the existing newline-delimited text body.
- Return covered errors as `application/problem+json` following RFC 9457.
- Never expose exception messages, causes, SQL, credentials, file paths, or stack traces.
- Use stable snake_case `errorCode` values and stable `urn:mightyetl:problem:*` type URIs.
- Scope the advice to `EtlController` so unrelated services and controllers do not change behavior.
- Preserve framework-owned routing, method, and response-negotiation status semantics.
- Preserve independent deployment and modular MSA compatibility.
- Add beginner-readable Javadocs and complete focused statement and branch coverage.
